# Vibe Research 工作接续

这里的“工作进程”是一个明确目标及交付物的工作单元，不是操作系统进程，也不等同于每次对话。以用户当前目标、研究库事实和现有授权为准。

## 入口与恢复现场

工作区提供 `outputs/open-workbench.py` 与 `outputs/projects.json` 时，用 Python 3.9+ 打开固定入口（macOS/Linux 通常是 `python3 outputs/open-workbench.py`，Windows 通常是 `py -3 outputs/open-workbench.py`）；迁移包路径不同则先定位这两个文件。它会复用同一工作区的服务，离线时重新启动。固定地址为 http://127.0.0.1:8766 。在最终交付和需用户查看过程时提供入口链接；不要声称服务永久在线或助手一直工作。

用 `vr hub list --registry <projects.json>` 选择明确登记的项目。不要因名称相同而把原项目、备份与迁移副本当成同一个项目；不扫描登记用户未指定的目录。

以下 `vr` 均指实际启动器，并带 `--project <项目目录>`。先读取 `work status`、`work history`、`status`；按当前目标选择工作，再用 `work recover W编号` 查看其目的、最近过程、阻塞及产物。历史支持 `--since YYYY-MM-DD --until YYYY-MM-DD --offset N --limit N`，日期按 UTC 最后更新时间，超过一页继续翻页；最近一条未必与本次请求有关。

## 新建还是继续

- 同一项目、同一未完成目标、交付范围未变：继续原工作。补充要求、修正、状态询问、切换助手或跨天本身不构成新目标。
- 已暂停但目标仍相同：核对现场后 `work resume W --message '恢复依据与实际发现' --next-step '下一步'`。它保留原编号和历史。
- 目标已完成，用户要求新的交付物、独立阶段或后续研究：`work start ... --previous W --reason '新目标与前序关系'`，保留关联。已结束的工作不重新改写为进行中。
- 旧目标未完成但用户切换到独立任务：先 `work pause W --message '暂停原因与已留下的内容' --next-step '恢复条件'`，再开始新工作。有明确继承关系才加 previous，不把所有任务串成假因果链。
- 用户明确替换/放弃旧目标：可 `work finish W --state superseded --message '用户替换目标及保留产物' --next-step '新目标'`，然后新建关联工作。暂停、被替代不冒充完成或失败。
- 跨研究项目：选择或经用户任务授权初始化、登记对应项目；各项目工作独立，不在旧项目挂新研究问题。前序编号仅支持同项目。

每个项目最多一个进行中/等待/阻塞工作；暂停项可保留多个。若另一项仍活动，先依据用户意图明确暂停/结束，不绕过 CLI 限制。

## 长时间离开后的判断

2 分钟无更新只表示无法确认仍在执行。24 小时无更新是完整恢复核验提示，不是自动分割目标的规则；短时间内环境变化也要核验。

恢复前检查：用户现在的目标是否改变；关联原文/产物是否存在；研究 revision 与代码版本是否变化；旧阻塞是否解除；旧训练/服务是否真的仍运行。不要看到旧的 working 就声称正在工作，不重复提交可能仍运行的训练。

如果目标和依据仍有效，继续原编号，并在 resume/update 中记录检查发现。原目标已结束或用户改变目标则新建。若之前等待的是必要用户答复，时间流逝不等于答复；保留等待并说明缺什么。只有缺失信息实质影响下一步才提问，独立可做的核对继续进行。

## 可读记录

工作开始写目标、意义、下一步；实质发现、落盘或改变方向时 update 并用 --nodes 关联真实产物。暂停时写已完成部分与恢复条件；结束时写交付与限制。不要用永久心跳、百分比或原始命令流伪造进展。状态询问如未实际恢复任务，不执行 resume。

研究状态只用 vr 修改。工作报告不当作证据；引文匹配、解释审阅和实验验证分开表述。不要为消除“待审阅”而批量接受证据。

## 新手与检索接续（2026-09-20）

固定入口已支持三步新项目向导：研究问题、来源选择、创建确认。已有项目直接进入，不因重开聊天重复引导。创建仅初始化研究库与保存来源偏好，不代表联网检索已执行；研究项目也不自动等同于 Codex 原生侧栏项目。`hub list` 返回 onboarding.providers，开始检索时沿用这些偏好；尚未核验或上次受阻的来源先通过 integrations 检查。

需多来源覆盖时用 `retrieval start --title ... --query ... --provider ... --include ...`（来源和查询可重复指定），随后显式运行 `retrieval launch` 或短时 `retrieval worker`。`retrieval status` 显示每来源游标、待补状态和 worker 存活情况。恢复前先读状态，再决定续跑；没有存活 worker 不承诺自动续查。`scout` / auto 的首个成功来源回退不能替代覆盖检索。发现型 Hugging Face 保留为范围待核查，不能计为完整覆盖。候选只有显式 `retrieval import` 才进入研究图。导入后必须做初筛；只要判定对当前问题有价值，就用 `reading triage ... valuable` 立即进入系统精读。恢复研究时先查看 `reading queue`：有全文的继续系统精读，无全文的先补全文并保留明确阻塞。精读证据仍需独立审阅，不能因初筛有价值就视为结论已验证。

归档和从入口移除保留文件，可通过 `hub restore` 恢复；先暂停当前工作和待补检索，等待 worker 退出。不要把“从入口移除”称为删除文件。目录迁移先登记以保存项目身份，移动后用 `hub relocate` 验证身份并保留旧链接。物理回收站和永久删除尚未交付。原生 Codex 项目映射用 `hub bind-codex` 保存真实宿主项目 ID 与根目录；先从 list_projects 核验，不推测 ID、不冒充已创建宿主项目。


工作台覆盖卡片已提供暂停、恢复、逐源重试/排除与显式启动后台。恢复状态不会自动启动联网；没有自动可处理项时执行器退出。用户查看候选时优先使用可读覆盖报告，而非原始 JSON。

跨项目关系用 `hub relate`（derived_from / related_to / reproduces）记录原因与目标当时 revision；派生关系不允许环，不把主题相关自动解释为派生。研究备份用 `bundle create`，恢复用 `bundle restore --destination <新目录>`；包含图、历史、队列和附件，不含外部代码与 Codex 任务。恢复后先核验身份、产物、连接和原目标，旧工作与检索保持暂停，不承诺自动续跑。


## 凭据、网络与分发接续

`integrations setup --provider <来源>` 在本人交互终端中不回显输入；macOS 默认系统钥匙串。不要把 key 当命令参数或写入聊天；钥匙串失败不自动降级，既有明文文件不会自动迁移或删除。配置元信息不是连接成功证明。

新项目向导会对所选来源做真实只读预检，并同时检查 PDF 精读运行时；预检不导入文献，也不证明全文权限。凭据可在本机工作台保存，不能要求用户粘贴到聊天。WoS 与 Scopus 已进入持久分页检索，仍须分别核验本人 key、机构 entitlement 和执行主机网络；Unpaywall 在候选出现 DOI 后作为开放全文定位任务加入，不做关键词覆盖。`integrations context` 记录本人确认的网络条件；环境指纹、用户保存的网络条件变化或超过 24 小时会提示复测，但不能声称已自动检测所有 Wi-Fi 切换。未配置权限时保留来源缺口，不默默排除。

`integrations diagnostics <新文件>` 导出白名单状态供本人查看，不含研究题目、查询、目录、原始错误和凭据，不自动上传。插件包与用户研究目录分离；分发包的同机新目录验收不等同于 Codex 安装成功或另一台实机验收。
